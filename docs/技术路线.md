# 技术路线：dsh-blender-mcp-bridge v1

> 日期：2026-10-18
> 定位：DSH 的 host 插件，直接连用户**当前打开的 Blender**（官方 `mcp` 扩展的套接字），在活会话里做**可撤销、可审计、不保存**的辅助创作。
>
> 一句话架构：**DSH 插件（Node）↔ TCP 127.0.0.1:9876 ↔ Blender 官方 mcp 扩展**。
> 不运行官方 MCP server，不实现 MCP，不 spawn Blender。

---

## 1. 目标与非目标

### 目标

1. 在用户**眼前正在编辑**的场景里读、改、渲染，不碰磁盘上的旧副本。
2. 每次写操作自动留一次撤销步骤，用户按 `Ctrl+Z` 能逐步回退。
3. **绝不保存**用户当前的 `.blend`；所有写盘只落在任务目录。
4. 任务目录固定为 `<当前 .blend 所在目录>/.dsh-blender-<任务名>/`；未保存工程落 DSH 会话 workspace；默认留 3 代快照。
5. 给模型提供**整窗截图 + 可控预览渲染**，让模型能看见自己改了什么、出图是什么样。
6. 给模型提供当前 Blender 版本的英文官方手册入口，让它自己查，不内嵌语料。
7. 自带 26 个 helper 和独立 Python 执行链，不依赖 `dsh-blender`；23 个常规 helper 直接可用，3 个维护类默认关闭。
8. 与 `dsh-blender` 分工明确、工具名不冲突；插件/包/id 全局统一 `dsh-blender-mcp-bridge`。
9. 所有面向模型的文本（工具描述、结果、错误、system prompt、skills）用英文；`docs/` 设计文档仍用中文给主人看。

### 非目标

- 不做沙箱，不宣称“保护你的数据”。动态构造、`ctypes`、`importlib.reload` 都能绕过。
- 不做 MCP 客户端/服务器，不引入 `blender-mcp` 的 Python 环境。
- 不做后台批处理（那是 `dsh-blender` 的活）。
- 不做浏览器设置页；配置走 profile patch。
- 不做全局 guard 去拦别的工具；只守自己的 `blender_mcp_*`。

## 2. 架构

```text
┌────────────────────────────── DSH 进程（Node） ──────────────────────────────┐
│  index.js  apply(ctx, config)                                                │
│   ├─ systemPrompt.section()   安全规则 + 工具分工 + 文档入口                 │
│   ├─ tools.register()         status / inspect / exec / snapshot / capture / render / helpers / helper │
│   ├─ session/event            turn/start：记轮次，决定快照时机               │
│   └─ skills.register()        （可选）live-session 技能壳，见 §14           │
│                                                                              │
│  lib/protocol.js    TCP 客户端：JSON + 0x00，一次连接一次请求                │
│  lib/handshake.js   握手：版本 / filepath / dirty / 对象数 / undo_steps      │
│  lib/taskDir.js     任务目录：路径、slug、属主标记、快照清单                 │
│  lib/snapshot.js    快照：copy=True、压缩、轮换（默认 3 代）                  │
│  lib/capture.js     整窗截图：写任务目录，不改场景                          │
│  lib/render.js      预览渲染：显式参数、逐项还原、只写任务目录              │
│  lib/helperCatalog.js helper 清单、参数 schema、依赖检查                    │
│  lib/pythonRuntime.js 探测 analysisPython、缓存依赖状态                     │
│  lib/helperRunner.js 白名单 helper 执行：Python 子进程或 Blender 内部 exec  │
│  lib/policy.js      静态拒绝：保存/打开/退出/偏好/明显越界路径               │
│  lib/guardPayload.js 生成 Python 运行时守卫（随每次 exec 发送）              │
│  lib/audit.js       audit.jsonl + 用户 .blend mtime/size 对比                │
│  lib/tools.js       八个工具的领域逻辑：结果形状、错误分型、截断             │
│  requirements-analysis.txt  numpy / Pillow / OpenCV / SciPy                 │
│  scripts/setupAnalysis.js   创建 .venv 并安装依赖（用户显式运行）           │
└──────────────────────────────────┬───────────────────────────────────────────┘
                                   │ TCP localhost:9876
                                   ▼
┌──────────────────────── Blender 进程（用户活会话） ──────────────────────────┐
│  官方 mcp 扩展：timer 每 0.25s（空闲 1s）poll 一次                            │
│  收到 execute → 主线程 exec(code) → JSON 响应 + 0x00 → 关闭连接              │
│                                                                              │
│  我们随代码注入的守卫（仅本次 exec 生效）：                                   │
│   - bpy.ops 模块级代理：拦保存/打开/退出/偏好                                │
│   - bpy.data.libraries.write 代理                                            │
│   - builtins.open / io.open / os / shutil / pathlib 写删钩子                 │
│   - 只允许写任务目录；其余抛结构化 PermissionError                          │
│   - finally：bpy.ops.ed.undo_push() + 收尾自检                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

**两个进程，一条套接字。** 主通道不启动子进程，也不需要用户自己准备 Python/uv 环境。

例外是 helper：Python 类 helper 由 Node 侧另外 `spawn` 一个 `analysisPython` 子进程；它只运行随包脚本、只接受 catalog 参数、输出只落任务目录。这条链不依赖 `dsh-blender`，也不经过 Blender 的 exec 通道。

前提：DSH 和 Blender 在**同一台机器、同一个文件系统**上。任务目录、快照、审计都由 Node 侧直接读写；如果将来要支持“Blender 在另一台机器”，这套落盘逻辑要整体重做。

## 4. 工具面

统一前缀 `blender_mcp_`，避免和 `dsh-blender` 的 `blender_*` 混；插件/包/id 全局统一 `dsh-blender-mcp-bridge`，工具名不再另起新前缀。

> 所有工具描述、结果字段说明、错误文本、system prompt、skills 正文都用**英文**。下面的中文是给主人看的设计说明。

### 4.1 `blender_mcp_status`（只读）

连接并握手，返回：

- `connected`、`host`、`port`；
- `blenderVersion`（如 `5.2.2 LTS`）、`versionMajorMinor`（`5.2`）；
- `filePath`（未保存为空）、`isDirty`、`background`、`onlineAccess`；
- `undoSteps`、`objectCount`、`activeScene`、`mode`；
- `renderSettings`：当前 width / height / resolutionPercentage / engine / samples（供“用户说用当前设置”时原样回传）；
- `taskRoot`、`taskDirs[]`（名字 + 最后修改时间）、`snapshots[]`；
- `docs`：`manualEn`（如 `https://docs.blender.org/manual/en/5.2/`）；
- 诊断：`peer`（是否像官方 add-on）、`warnings[]`。

只读工具**不创建任务目录**。

### 4.2 `blender_mcp_inspect`（只读）

结构化场景摘要：集合、对象类型计数、每个对象的父级/修改器/网格统计/材质。用于“改之前先看清”。

### 4.3 `blender_mcp_exec`（写）

参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `code` | string，必填 | 要在 Blender 主线程执行的 Python |
| `task` | string，必填 | 任务名，决定 `.dsh-blender-<slug>` |
| `description` | string，可选 | 本次改动的一句话说明，进审计 |

流程见 §5。返回：

- `status`: `ok` / `blocked` / `error` / `timeout`；
- `result`: 用户代码写入的 `result`（做 JSON 安全化与截断）；
- `stdout` / `stderr`（截断）；
- `undo`: `{pushed, message, error?}`；
- `snapshot`: `{path, bytes, tookMs}`；
- `guard`: `{blocked[], intact, window}`；
- `changes`: `{objectsAdded, objectsRemoved, objectsModified}`（有界聚合）；
- `warnings[]`、`handoffHint`（“未保存、可 Ctrl+Z、F12 出图、任务目录已保留”）；
- `suggestedPath`（仅 `blocked` 时给）：这次被拦的写法对应的合法落点，避免模型反复试探同一处。

**超时语义**：`responseTimeoutMs` 到点后连接会断，但 Blender 主线程可能还在跑那段代码，之后仍会 `undo_push`。所以超时返回 `status: 'timeout'` 并写明“代码可能仍在 Blender 内执行”；下一次 `status` / `exec` 开头先做一次轻量自检（dirty、`.blend` mtime、对象数），把“上一轮可能超时”作为 warning 带出来。

**误操作处理（硬规则）**：AI **不得自行回滚**——本插件不提供恢复工具，`open_mainfile` 一律拒绝。发现异常（文件被改、守卫被破坏、超时后状态不明、场景被改坏）时，AI 必须**告知用户并结束本轮**，把快照路径、现象和需要用户做的操作写清楚；回滚只能由用户手动完成（`Ctrl+Z` 或自己打开快照）。

### 4.4 `blender_mcp_snapshot`（写任务目录）

显式再存一代快照（重要节点用），参数 `task`、`label`。不改变当前会话。

### 4.5 `blender_mcp_capture`（写任务目录）

参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `task` | string，必填 | 任务名 |
| `label` | string，可选 | 截图名，默认 `window-<时间>` |

作用：从 timer 回调截**当前 Blender 窗口**（含 UI 面板），写到 `<任务目录>/captures/`。不改场景、不 push、不创建撤销步骤。

实现要点（已实测）：

- 直接用 `bpy.ops.screen.screenshot(filepath=<绝对路径>)`；`bpy.context.area` 为 `None` 时也能用，**不需要 temp_override**。
- 只依赖 `bpy.context.window`：`window` 为空会 `poll failed`；`screen` 为空不影响。后台模式一律 `poll failed`，直接给明确错误，不要在后台设计截图。
- 不要用 `screenshot_area`（不加 `temp_override(area=...)` 会静默写出 1×1、250 字节的废图）；`screenshot_window` 的属性名在，但 RNA 没注册，调用即失败（5.2.2 实测）。
- 截图**永远是 PNG**；文件名必须显式带 `.png`，路径用绝对路径。父目录不存在时 Blender 会自动建，但仍要先检查目录在任务目录内。
- 实测 1920×1009 整窗 551 KB，首次 123 ms、稳定 57–64 ms；编辑模式下也能截。

返回：

- `path`、`bytes`、`width`、`height`、`tookMs`；
- **图片块**：execute 里用 `ctx.attachments.saveImage({ data, mediaType:'image/png', name })` 拿 `ImageAttachmentRef`，value 带 `image` ref；`output.render` 返回“文本信封 + 原生 image 块”。形状固定为 `{ type:'image', attachment:{ attachmentId, mediaType, bytes, width, height, name? } }`，不要自己发明 base64 字段。
- **能力判断**：先看当前路由模型是否声明 `image` 输入（`ctx.get('llm').resolveModelInfo(provider, model, signal).inputModalities.includes('image')`）；不支持就**只返回路径 + 说明**，不要发一个会被静默替换成占位文本的图块。
- 限制：图片只收 PNG/JPEG/WebP/GIF；源图 ≤ 20 MiB、单边 ≤ 8192 px、总像素 ≤ 64M px；DSH 会归一化并可能缩到 4 MiB 左右。超过就报错并说明。

### 4.6 `blender_mcp_render`（写任务目录）

参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `task` | string，必填 | 任务名 |
| `width` | integer，必填 | 预览宽度，来自用户明确给出的值 |
| `height` | integer，必填 | 预览高度，来自用户明确给出的值 |
| `samples` | integer，必填 | 预览采样，来自用户明确给出的值 |
| `engine` | string，可选 | `BLENDER_EEVEE` 或 `CYCLES`；不传就用当前引擎；取值以运行时枚举为准（5.2.2 工厂启动只有 `BLENDER_EEVEE`，`CYCLES` 取决于用户是否启用 Cycles 插件） |
| `resolutionPercentage` | integer，可选 | 默认 100 |
| `camera` | string，可选 | 相机对象名；不传用场景当前相机，没有就报错，不自动建相机 |
| `label` | string，可选 | 文件名 |

实现要点（已实测）：

- `bpy.ops.render.render(write_still=True)` 同步出图，返回 `FINISHED`；预览尺寸下很快（640×360/16 samples 热渲染 0.11 s），但**本机冷 Shader 缓存第一次可能 17 s**，所以这个工具的超时按 **≥120 s** 设计，并提示“正在渲染、Blender 界面会短暂卡住”。连续预览会快。
- 渲染前记录、`finally` 里逐项还原：`resolution_x/y/percentage`、`render.filepath`、`image_settings.file_format`、`engine`、`eevee.taa_render_samples`、`cycles.samples`、`cycles.use_denoising`。实测还原后 `diff = {}`；没相机抛错也照样还原，且不写文件。
- 渲染**不产生 undo 步骤**、不置 dirty、不改 `bpy.data.filepath`；只多一个 `Render Result` 内存数据块。
- 输出路径必须是“任务目录内 + 绝对路径 + 明确文件名 + 扩展名”；不要传目录、不要传 `####`（不会展开）、不要传 `//`（会按 blend 目录解析）。Blender 会自动建缺失父目录，所以写前用 `bpy.path.abspath` + `os.path.realpath` + `os.path.commonpath` 判定在任务目录内。
- 为了返回图片块，预览输出格式临时用 PNG（`image_settings.file_format='PNG'`），渲染后恢复原值；这是“临时且还原”的改动，不是替用户改设置。
- 返回路径、字节数、耗时、实际使用的参数；图片块规则同 `capture`；模型不支持图片时降级为路径。

### 4.7 `blender_mcp_helpers`（只读）

列出 23 个常规 helper：

- `name`、`module`、`description`；
- `runtime`（`blender` / `python`）、`dependencies`；
- `ready`、`missing`；
- 参数 schema（名称、类型、是否必填、路径方向）。

维护类 3 个默认不出现；`enableMaintenanceHelpers: true` 后才列出。

### 4.8 `blender_mcp_helper`（写任务目录）

运行一个 helper：

| 参数 | 类型 | 说明 |
|---|---|---|
| `name` | string，必填 | helper 名，必须在 catalog 中 |
| `task` | string，必填 | 任务名，决定输出目录 |
| `args` | object，必填 | helper 参数，按 catalog 校验 |
| `timeoutMs` | integer，可选 | 覆盖默认超时，有上限 |

执行分两路：

- `runtime: 'blender'`：`surface-texture-coverage-audit` 通过插件内部 exec 运行，只读、不 push、不写场景；
- `runtime: 'python'`：Node 用 `child_process.spawn(analysisPython, [script, ...args])` 启动独立进程，不用 shell；只运行 catalog 内脚本。

返回 `status`、`report`（stdout 是 JSON 时）、`stdout/stderr` 摘要、`outputs[]`、`durationMs`；输出图片按 `capture` 的图片块规则附给模型。

路径与安全：

- 输入只能在会话 workspace、当前 `.blend` 所在目录或任务目录内；输出只能在任务目录内；
- 不允许 AI 传脚本路径或 Python 代码；
- 超时默认 120 s，输出上限 200k 字符；
- 维护类默认关闭；
- 详细设计见 [`helper-runtime.md`](helper-runtime.md)。

> 工具数量：status / inspect / exec / snapshot / capture / render / helpers / helper，共 8 个。不设 `docs` 工具——知识入口放在 `status.docs` 和提示词里，抓取交给宿主已有的 `web_fetch`。

## 5. 一次写操作的流水线

```text
0. 写锁（Node 侧）
   写类工具（exec / snapshot / capture / render / helper）共用一把进程内互斥锁，只读工具不锁
1. 握手
   连接 → exec 只读握手代码 → 校验版本/对端 → 拿 filePath / dirty / undoSteps / renderSettings
2. 任务目录
   filePath 有目录 → <dir>/.dsh-blender-<slug>/
   filePath 为空 → 落 DSH 会话 workspace（主人已定）
   已存在且无属主标记 → 视为他人数据，追加 -2 / -3
3. 静态检查（Node 侧）
   明显保存/打开/退出/偏好/越界路径 → 返回 blocked，代码根本不发；被拒的调用不消耗快照代次
4. 快照（本轮首次写之前）
   还没有本轮快照 → save_as_mainfile(copy=True, compress=True)
   写盘失败 → 直接拒绝执行（没有备份就不写）
5. 执行（Blender 侧，带守卫）
   安装 bpy.ops / bpy.data.libraries / 文件写删钩子
   try: 执行用户代码（compile 文件名 <dsh-user-code>，行号可读）
   finally: bpy.ops.ed.undo_push(message="dsh-blender: <task>")
            收尾自检、卸钩子、汇总 blocked 证据
6. 事后审计
   stat 用户 .blend（mtime/size）与 .blend1
   变了 → warnings/incident，附快照路径；绝不悄悄放过
   写 audit.jsonl
7. 返回
   结果 + undo + snapshot + guard + changes + handoffHint
```

**为什么快照在 exec 之前单独做**：快照本身是“受信任的保存动作”，不该出现在用户代码的守卫作用域里；分开做，守卫就可以一律拒绝保存类算子，规则更简单。

**为什么 undo_push 在 finally**：用户代码可能中途抛错，但前面已经改了场景；push 一下，至少这些半截改动能 Ctrl+Z 回去。

**为什么写类工具要串行**：模型可能并行发起两个写调用；Blender 主线程虽然把代码串行执行，但 Node 侧的“快照 → 执行 → 审计 → 轮换”顺序会被打乱，快照可能对不上执行顺序。串行化后每条链路都完整。

## 6. 安全设计

### 6.1 四层，如实标注

| 层 | 位置 | 作用 | 是不是边界 |
|---|---|---|---|
| 提示词 | system prompt | 告诉 AI 不要保存、不要越界、怎么分工 | ❌ |
| 静态拒绝 | Node 侧，发送前 | 明显的保存/打开/退出/偏好/越界路径直接不发 | ❌ 只防直白写法 |
| 运行时守卫 | Blender 进程内，同一次 exec | `bpy.ops` 代理 + 文件钩子，动态构造也能拦 | ⚠️ 唯一有点实际作用的层，但仍可绕过 |
| 事后审计 | exec 前后 | 用户 `.blend` 是否被动过、守卫是否完整 | ❌ 只报告 |

### 6.2 运行时守卫拦什么

**算子（`bpy.ops` 模块级代理）**

- `wm.save_mainfile`
- `wm.save_as_mainfile`（用户代码里一律拒绝；快照走独立的受信任请求）
- `wm.save_homefile` / `wm.save_userpref`
- `wm.open_mainfile` / `wm.read_homefile` / `wm.read_factory_settings` / `wm.read_factory_userpref` / `wm.read_userpref`
- `wm.quit_blender`
- `preferences.*` 的写入口
- 文件输出算子（`render.render`、`export_scene.*` 等）：检查目标路径必须在任务目录内

**文件 API**

- `builtins.open` 与 `io.open` 指向同一个钩子（只包一个会漏）
- `os.open` / `os.remove` / `os.unlink` / `os.rename` / `os.replace` / `os.rmdir` / `os.mkdir` / `os.truncate`
- `shutil.copy*` / `move` / `rmtree`：**任一实参越界就拒**
- `pathlib.Path.write_text` / `write_bytes` / `open` / `unlink` / `rename` / `replace`
- `bpy.data.libraries.write`

判定用 `realpath` + 大小写归一化，只放行任务目录及其子目录。失败抛结构化 `PermissionError`，返回里列出 `blocked[]`。

**三条实现硬约束**（旧实现踩过的坑）：

1. **不要包 `bpy.ops._op_create_function`**：上游弱沙箱每次 exec 结束会把它还原，补丁活不过一次请求。用 `bpy.ops` 模块级代理。
2. 代理必须**读写透传** `_op_create_function`（上游 `__enter__` 读、`__exit__` 写），非名单算子必须委托给**当前**的 `_op_create_function`。
3. 代理只在本次 exec 安装，收尾卸下；重装要剥掉旧钩子，根目录变化要强制重装。

### 6.3 明确做不到的

- 不防刻意绕过：`importlib.reload`、`ctypes` 直调 C、动态构造路径、异步任务在 exec 返回后的落盘。
- 不审计 Blender 的出站网络流量。
- 不保证多实例下连到“用户眼前那个” Blender；只能握手后让用户确认。
- 不保证保存拦截 100%：事后 mtime 审计是兜底，不是预防。

提示词和 README 都必须写这几句，不许出现“安全沙箱”“已保护数据”。

### 6.4 与 DSH 审批、全局 guard 的关系

按主人决定：**安全防护只守自己的工具**。

- 不注册全局 `ctx.tools.guard()` 去拦 `pwsh` / 文件工具 / 别的插件；那会误伤用户正常操作，也让责任边界变糊；
- 所有检查都在 `blender_mcp_*` 的 `execute` 和随 exec 发送的 Python 守卫里做；
- DSH 的 `tools/pre-execute` 审批不作为关键防线（审批通道不一定可用，没有 answerer 时 fail-closed）；最多对明显高危的 `blender_mcp_exec` 返回 `ask`，拿不到审批就拒绝，行为仍然安全。

### 6.5 失误处理：只报告，不自行回滚

- 本插件**不提供恢复工具**；`open_mainfile` 在用户代码里一律拒绝，快照只写不读；
- 发现异常（文件被动过、守卫被破坏、超时后状态不明、场景明显改坏）时，AI 只做三件事：**停下、说清楚现象和快照路径、结束本轮**；
- 回滚只能由用户手动完成：`Ctrl+Z`，或用户自己打开任务目录里的快照；
- 为什么不自动回滚：回滚本身又是一次不可审的写操作，容易把现场弄得更乱，也绕开了“用户知情”这条底线。

## 7. 撤销与快照

### 7.1 撤销

- 每次 `blender_mcp_exec` 末尾在 `finally` 里 `bpy.ops.ed.undo_push(message="dsh-blender: <task>")`；
- 一次 exec = 一个 Ctrl+Z 步骤（实测；算子的内部 push 在 timer 回调里不产生步骤）；
- 不 push 就没有撤销步骤，所以这一步不能省；
- push 会把会话置 dirty，这是正确语义，插件不复位 `is_dirty`；
- 撤销栈默认 32 步；长会话早期步骤会被挤掉，重要节点用快照；
- 撤销会把用户从编辑模式踢回对象模式，工具描述里提前说；
- push 失败（极少见）时返回 `undo.pushed: false` + warning，不谎称可撤销。

### 7.2 快照

- 位置：`<任务目录>/snapshots/<turn>-<seq>.blend`；
- 时机：默认每轮首次写操作之前；可配 `snapshot.on = 'turn' | 'write'`；
- **代次**：默认 3 代，可配 1–20（主人说的“自定义保存快照代次”就是这一项）；
- 轮换：**先写第 n+1 代，成功后再删最旧的**，任何时刻不先删后写；
- 压缩：默认 `compress=True`（实测更小更快）；
- 失败：写盘失败 = 拒绝本次写，不允许“没备份继续”；
- 限制：完整 `.blend`，不自动打包外部贴图/链接库；大工程耗时未压测；v1 不做体积上限，快照大小写进返回和审计，用户可据此清理。

## 8. 任务目录与审计

### 8.1 目录

```text
<blendDir>/.dsh-blender-<task>/
├── snapshots/          # 默认 3 代
├── captures/           # 整窗截图
├── renders/            # 预览渲染
├── exports/            # 导出
├── audit.jsonl         # 每次 exec 一行
└── .dsh-blender-task.json   # 属主标记：sessionId、task、createdAt
```

- 任务名由 AI 给，slug 化：保留中英文数字，剥路径分隔符/控制字符/Windows 保留名，上限 48 字符，空则 `task`；
- 当前 `.blend` 没有路径（未保存）时，任务目录落到 DSH 会话 workspace，并在返回里明确说明；
- 目录已存在且无属主标记 → 视为别人的数据，追加 `-2`、`-3`；
- 目录不自动删除；`status` 只读列出同级 `.dsh-blender-*`，目录太多时 AI 询问用户是否清理，删除由用户自己做；
- 只读工具不建目录。

### 8.2 审计

每条 exec 一行 JSONL：

```json
{"time":"...","sessionId":"...","turn":3,"task":"lamp","codeSha256":"...","code":"...","status":"ok","blocked":[],"snapshot":"...","undo":true,"dirty":true,"durationMs":812,"fileChanged":false}
```

- `code` 默认存（`audit.storeCode=true`），可配置关闭；
- `fileChanged` 来自用户 `.blend` 前后 mtime/size 对比；
- 真被保存了：返回 `warnings` + `incident`，附快照路径，不自动恢复。

## 10. 与 `dsh-blender` 共存

### 10.1 工具名

插件/包/id 全局统一 `dsh-blender-mcp-bridge`；工具统一 `blender_mcp_*`；`dsh-blender` 是 `blender_*`。不重名，模型仍有概率选错，所以每个工具描述第一句都写“operates on the user's current live Blender session”。

### 10.2 提示词分工

| 场景 | 用哪个 |
|---|---|
| 改用户眼前这个场景、怕丢未保存工作 | `blender_mcp_*` |
| 分析/校验/批量导出磁盘上的 `.blend` | `dsh-blender` 的 `blender_*` |
| 需要后台进程保存版本化 `.blend`、跑批量流水线 | `dsh-blender` |
| 参考图/线框/多视图/UV/外观 QA | 本插件的 `blender_mcp_helpers` / `blender_mcp_helper` |
| 查官方手册 | `blender_mcp_status` 的 `docs` + `web_fetch` |

明确写：

- **不要**用 `blender_python` 去改用户当前打开的会话（它看不见未保存改动，还会保存文件）；
- **不要**在本插件的 `exec` 里保存 `.blend`；
- 两边同时操作同一工程会分叉，先问用户用哪边。

### 10.3 版本与端口

- `dsh-blender` v0.2.3 只声明兼容 DSH `0.2.0-rc.2` / `0.2.1-alpha.1` / `0.2.1-alpha.2`；本机 rc.2 需实测；
- 它不开控制端口，不会抢 9876；但要确保它的后台 Blender 不启用 `mcp` 扩展，否则会出现多个 9876 监听；
- Windows 上多 Blender 可同时监听 9876，连接落到先启动者；本插件靠握手显示 `filePath`，多实例时让用户改端口。

## 11. 配置

`cordis.patch.yml` 列全集（patch 整块替换，不深合并）：

```yaml
- insert:
    - id: dsh-blender-mcp-bridge
      name: dsh-blender-mcp-bridge
      config:
        host: 127.0.0.1
        port: 9876
        connectTimeoutMs: 5000
        responseTimeoutMs: 30000
        captureTimeoutMs: 30000
        renderTimeoutMs: 120000
        maxResponseChars: 200000
        taskRootMode: blendFile      # blendFile | workspace
        taskRoot: ''
        snapshot:
          enabled: true
          generations: 3             # 快照代次（1–20）
          on: turn                   # turn | write
          compress: true
        guard:
          enabled: true
        helper:
          analysisPython: ''       # 空 = 自动探测 python / python3 / py -3
          autoDetectPython: true
          timeoutMs: 120000
          maxOutputChars: 200000
          enableMaintenanceHelpers: false
        audit:
          enabled: true
          storeCode: true
```

- 配置 schema 用 schemastery；非法值加载期失败；
- `taskRoot` 非空时固定用它，忽略 `taskRootMode`；为空时按 `taskRootMode` 推导（`blendFile` = 当前 `.blend` 目录，`workspace` = 会话 workspace）；
- `snapshot.on = turn` 表示每轮首次写之前落一代，`write` 表示每次写之前都落；
- `guard.enabled=false` 只关 L2 运行时守卫；L1 静态检查、快照、`undo_push`、审计照常，不能借此变成无保护执行；
- 超时分工：`exec` 用 `responseTimeoutMs`（默认 30 s）；`capture` 用 `captureTimeoutMs`（默认 30 s）；`render` 用 `renderTimeoutMs`（默认 120 s，覆盖冷 Shader 缓存）；helper 用 `helper.timeoutMs`；
- `render` 的 `width` / `height` 必须为正且不超过 8192，`samples` 必须为正；超出直接报错，不偷偷改；
- `helper.analysisPython` 设了但不可用时直接报错，不偷偷回退；自动探测失败时给安装提示；
- 每个键都必须有消费者，禁止“看起来实现了”的死配置；
- 不做设置页；模型侧固定英文，不提供语言开关。

## 13. 实现语言：要不要用 TypeScript

**结论：v1 不需要 TS 源码；用纯 JS + JSDoc + `checkJs`，再补一份薄薄的 ambient `.d.ts`。**

实际查到的类型情况：

- 本机安装包是 asar，`@deepseek-ai` 的 6968 个条目里 **`.d.ts` 数量为 0**；但每个包的 `package.json` 仍写着 `"types": "lib/types/index.d.ts"`，文件实际上不存在。
- 官方类型以字符串形式躺在 `lib/typert.host.js` 的 `"declaration"` 字段里，不是给 TS 用的文件。
- 因此 `import { defineTool } from '@deepseek-ai/dsh-tools'` 在严格 TS 里会报“缺声明”，JSDoc 也只能退化成 `any`。

推荐方案：

- `jsconfig.json` 开 `checkJs`、`strict`、`noEmit`；用 `tsc --noEmit` 做门禁。
- 写一份 `types/dsh.d.ts`，只声明我们真正用到的面：`defineTool`、`Schema`、`ctx.tools/systemPrompt/skills/attachments/llm`、`session/event`、`agent/pre-step`、`createUserMessage`、`ImageAttachmentRef`。用到哪个补哪个，别一次写全。
- 不给官方包手写运行时替代品；类型只是开发期检查。

为什么不改 TS：

- profile 只加载 `main` 指向的 JS；TS 必须多一步构建，host 半本来零构建。
- AGENTS 明确要求 JSDoc + `checkJs`；改 TS 反而破坏约定。
- 本机 Node 24 能直接跑 `.ts`，但插件跑在 Electron 里，不能赌。

**什么时候才考虑 TS**：插件拆成多个包、需要对外发布类型、或团队统一 TS。现在不需要。

## 14. 能不能内嵌 `create-3d-model` 作为技能库

**结论：技术上能；更建议“借知识、不照搬”，用不同的技能名，精选子集。**

注意：官方没有单独发布“精简包”，只提供完整的 30 件套；`capability-map.md` 给的是按场景推荐的加载顺序，不是打包好的子集。下面的精选是**我们自己按活会话约束做的裁剪**。

完整的内容分类和引用范围见 [`refer-create-3d-model.md`](refer-create-3d-model.md)。这里只留实现要点。

### 14.1 DSH 的技能注册长什么样

`inject: ['skills']` 后：

```js
ctx.effect(() => ctx.skills.register({
  name: 'blender-live-session',            // 必须 kebab-case：^[a-z0-9]+(?:-[a-z0-9]+)*$
  description: '...',                      // 必填
  whenToUse: '...',                        // 可选
  source: 'dsh-blender-mcp-bridge',        // 必填，字符串标签
  content: '...markdown...',               // 必填，正文
  resourceBase: { kind: 'directory', path: ... }, // 可选，引用资源目录
}), 'blender: skills')
```

- `name` 不合规直接抛 `Error: invalid skill name`；
- `source` / `content` 缺了 `register` 不报错、`list()` 也显示，但 `get()` 会抛 `TypeError`——必须给全；
- 同层同名是**先到先得**：后来者只 warn，disposer 是空操作，不覆盖、不报错；
- 想查重：`await ctx.skills.list({ cwd })` 或 `snapshot()`，看合并后的赢家；
- 纯 host 插件就够；模型侧还要靠基础组装里的 `dsh-tool-skill`（桌面版默认有）把目录放进消息、提供 `skill` 工具。

### 14.2 为什么不原样搬

- 上游 `create-3d-model` 按 BlenderMCP/Codex 的语义工具写：`get_scene_info`、`get_object_info`、`get_viewport_screenshot`、`execute_blender_code`；本项目直接引用上游，再把这些能力映射到 `blender_mcp_*`。
- 上游的正文还会保存版本化 `.blend`；本插件是活会话 + 不保存 + Ctrl+Z，照搬会教模型做错事。
- 29 个领域技能里很多依赖参考图/线框/OpenCV/NumPy/Pillow/Helper 运行时；本插件自带独立 Python 链，但工具名和保存流程仍要改。
- 上游技能自报验证到 Blender 5.2.0；我们是 5.2.2，版本相关结论要自己复核。
- 和 `dsh-blender` 的技能同名会 first-wins；既然名字不重要，直接用不同名字最省事。

### 14.3 推荐做法

1. **名字错开**：用 `blender-live-session`（编排）和 `blender-live-*`（领域）这类名字，不跟 `create-3d-model` 撞。
2. **只注册 1 个编排技能**，正文用英文；把精选的参考文件放在 `resourceBase` 目录下，按需读取，不把 30 个技能全塞进目录。
3. **运行时 preamble 统一映射**：上游/BlenderMCP 的 `get_scene_info`、`get_object_info`、`get_viewport_screenshot`、`execute_blender_code` → `blender_mcp_inspect` / `capture` / `exec`；保存 → 快照 + Ctrl+Z；路径 → 任务目录；视觉 → capture/render；helper → `blender_mcp_helper`；不联网、不装插件、不改偏好。
4. **精选范围**：顶层流程、视觉验收、生产顺序、建模模式、常见尺寸、Blender 5 兼容，再加 6 个核心领域配方（建模/材质/灯光/相机/渲染/导出）。
5. **带 MIT 署名**：保留 `LICENSE` / `UPSTREAM_LICENSE`，在技能目录的 `LICENSES/` 和每个改写文件头写清来源与改动。
6. **v1 先不做 30 个技能**；先把工具、截图/渲染、护栏打磨稳，再按实际需要扩。

如果坚持完整 30 个技能，也能做，但要接受包体、逐条工具映射、helper 依赖、与 `dsh-blender` 的 first-wins 关系，以及后续跟上游维护。

### 14.4 helper 怎么处理

v1 直接加入 helper，并自带独立 Python 执行链，不依赖 `dsh-blender`。

- **23 个常规 helper 全部进工具面**；3 个维护类随包保留但默认隐藏，`enableMaintenanceHelpers` 打开后才可用。
- **Blender 运行时 helper**：`surface-texture-coverage-audit` 走插件内部 exec，只读、不 push。
- **Python helper**：Node `spawn` 独立的 `analysisPython`，只运行 catalog 内脚本；参数校验、路径限制、超时、输出上限都在 Node 侧做。
- **依赖**：`requirements-analysis.txt` 列 numpy / Pillow / OpenCV / SciPy；`scripts/setupAnalysis.js` 创建 `.venv` 并安装。缺依赖时明确报缺失模块，不自动安装。
- **参考锁定模块**：`wireframe-to-3d`、`reference-to-3d`、`multiview-*`、`atlas-uv-fitting`、`closed-surface-uv-coverage`、`texture-*` 的 helper 脚本随包放在 `helpers/`，核心 references 在 `skills/blender-live-session/references/`；29 个领域模块的 `SKILL.md` 正文 v1 暂不随包，后续版本再补。自动化流程在依赖齐全时可用。
- **不共享 `dsh-blender` 状态**：两边的 helper 各跑各的，不互相调用，也不要求对方安装。

详细设计、参数校验、安全边界和验收见 [`helper-runtime.md`](helper-runtime.md)。

引用与署名见 [`refer-create-3d-model.md`](refer-create-3d-model.md)，不在设计文档里重复。
